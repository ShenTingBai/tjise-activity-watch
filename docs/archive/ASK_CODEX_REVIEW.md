## 一、我最关心的三个问题

1. 这套方案**是否合理**？核心设计决策站不站得住？
2. 它是不是一个**好的**解决方案？（不只是"能跑"，而是可维护、可观测、出问题能发现）
3. 是否存在**明显更优的方案**？如果有，具体是什么、好在哪、代价是什么？

## 二、约束条件（请严格遵守）

提出任何建议前先看这里。脱离下列约束的方案一律不适用，
除非你能论证其收益显著超过成本。

- **单人维护的学生项目**，不是生产级系统，没有团队、没有值班
- **一台 1 核 2G 的 Linux 云服务器**，无数据库，状态存放在 JSON 文件里
- **数据源没有官方 API**：接口靠抓包获得，登录态存在浏览器 localStorage，
  token 有效期仅数小时，需用无头浏览器在服务器端续期
- **目标用户是一个宿舍群**（十余人量级），不是大规模分发
- **不能对学校系统造成压力**（当前约 305 次请求/天）
- **不具备 7×24 运维能力**，出问题往往几小时后才会被发现

因此以下方向默认不适用：引入 Kafka / Redis / PostgreSQL / Kubernetes、
做微服务拆分、要求学校开放官方 API、增加专职运维流程。

## 五、逐条质疑关键决策

以下是已经做出的设计决策。请对**每一条**给出
「认同 / 反对 / 有条件认同」，并说明理由与依据位置。
若认为某条是错的，直接说「这个决定错了」，不要用「可以考虑……」这类模糊表述。

1. 系统里放**两个机器人**：自定义机器人（webhook）只负责定时推送，
   应用机器人（长连接）只在被 @ 时响应，两者职责不合并
2. 应用机器人**必须被 @ 才响应**；取不到自身 open_id 时按 fail-closed 处理（宁可启动失败）
3. 去重基线取「**已成功推送过的集合**」，且**推送成功后**才写入，而不是抓取时写入
4. 定时推送与 @ 回复**共用同一个渲染函数**，并有一致性自检逐字段比对
5. 定时推送的卡片**不带按钮**（webhook 卡片按钮回调不会回到应用，放了就是死按钮）
6. 报名冲刺扫描**每 5 分钟全天运行**，不降频，且**不缓存接口响应**
7. 清单推送时点维持 07:00 / 10:30 / 16:30 / 21:30（有 290 条数据统计支持）
8. 登录态用**无头浏览器在服务器端自动续期**（每 2 小时一次）
9. 不做「无变化精简推送」，每次都发完整清单
10. 用 JSON 文件 + 文件锁 + 原子写管理状态，不引入数据库

## 六、评审维度

- **合理性**：核心假设是否成立？推导是否自洽？有没有前后矛盾？
- **质量**：异常处理、边界情况、可观测性、失败是否静默、能否回滚
- **更优方案**：至少给出 **2 个**替代架构。不要只说"可以更好"，要给出具体设计
- **风险**：性能、安全（凭据管理）、可维护性、换学校时的改造面
- **成本**：每条改进要估计改动范围与是否可回滚

### 1. 方案理解复述
不超过 10 行。

### 2. 总体判断
一句话结论 + 分档（**优秀 / 合格 / 需重构 / 不成立**）+ 不超过三句核心理由。

### 3. 做对的地方
至少 3 条，每条附依据位置（文件路径 + 函数名或行号）。
说明「在什么条件下它是对的」，而不是泛泛表扬。

### 4. 问题清单
按严重度分级，每条格式：
`[P0/P1/P2] 问题 → 依据位置（文件:行/函数） → 为什么是问题 → 触发条件`

- P0：会导致功能错误、数据损坏、安全漏洞，或使目标无法达成
- P1：在异常或边界下会出问题，或明显损害可观测性/可维护性
- P2：优化项，不影响正确性

### 5. 更优方案
至少 2 个，分别给出：方案描述、与本方案的对比表
（改动范围 / 收益 / 成本 / 新引入的风险 / 为何更好）、以及推荐与理由。
若认为当前方案已是最优，说明考虑过哪些方向、为何都被排除。

### 6. 如果推倒重做
简版架构（不超过 20 行），说明与现方案的**本质差异**，
以及这个差异值不值得付出重写成本。

### 7. 改进清单（按优先级排序）
表格：
`优先级 | 问题 | 具体改法 | 改动范围与成本 | 验证方式 | 依据位置`

排序：P0 → P1 → P2；同级内按修复成本从低到高。

### 8. 需要补充的上下文
每条格式：`需要确认什么 → 影响上面哪条结论 → 若按最坏情况假设，结论如何变化`

**不得因信息不足而默认通过。** 无法验证的要显式列出或标注「待确认」。

## 八、硬性要求

1. **每条结论必须附依据**：文件路径 + 函数名/行号/字段名/文档章节号，或原文引述。

7. **只读**：全程不得修改任何文件。

## 用法说明

**启动位置**：在 `tjise-activity-watch/` 目录下启动 codex，提示词里的相对路径才能直接生效。
如果在上级 `activities/` 目录启动，把路径前缀统一改成 `tjise-activity-watch/`。

**为什么强调只读**：Codex 默认有写文件权限。不加这条，它很可能评审到一半就动手改代码，
你的仓库会被改得和报告对不上。提示词开头和第八节第 7 条各写了一次，就是防止这件事。

**为什么排除 config.json 和 data/**：前者含飞书 webhook 与密钥，后者含真实姓名学号。
评审架构不需要这些，给出去只会扩大暴露面。
