# 天软活动报名：报名时间队列

状态：待用户评审。本文描述目标设计，当前应用截图仍是上一版；静态视觉稿只用于评审，不代表已实现。

## 产品与设计目标

产品名：天软活动报名

副标题：登录一次，选好活动，开放时自动提交

主要用户是使用学校活动网站的学生。界面要让人快速确认登录是否有效、哪些活动尚未报名、下一次报名何时开放，以及当前选中活动的操作结果。设计核心是校园活动的时间顺序：它是一张可操作的报名队列，不是“统计横幅 + 数据表 + 详情侧栏”的管理后台。

设计原则：

- 用具体活动、地点和开放时刻作为信息主体；品牌标识轻量，避免内部代号、全大写英文眉题和“值守台”等运维术语。
- 让活动队列占满主工作区。活动行可多选并加入报名计划；同一开放时刻按组呈现，计划摘要与启动操作固定在底部，不在侧栏重复展示活动详情。
- 倒计时只表达真实时间差，不显示无来源的进度百分比。没有明确时间时，明确说等待时间公布。
- 颜色同时承载状态含义和阅读层级；按钮文案描述实际动作，成功或失败反馈给出下一步。
- 示例活动名称、地点、时间均为视觉稿中的虚构内容，不可当作实时数据。
- 页面始终区分两种时间关系：报名开放时间决定何时提交，活动举办时段决定所选活动能否共存。相同开放时间不代表举办时间重叠。

## 方案推导

上一稿只是把常规后台的摘要卡换成开放时刻横幅，底层仍是左列表、右操作栏；这不是信息架构上的改变。新方案采用全宽垂直报名时间队列：活动沿开放时间排列，每行可独立加入或移出计划；相同开放时刻的活动放进同一时间组。底部计划条汇总已选活动、同时开放的组数和计划状态，启动操作也在此处。这样可以一次预排多场活动，同时保留清楚的先后关系。

队列里的开放时间组只表达报名提交时刻，不表达活动是否冲突。活动是否冲突需比较完整的举办起止时段，并对整个报名计划检查；活动开放时间相同但举办时段不重叠时可以同时选择，开放时间不同但举办时段重叠时也应提示冲突。尝试加入与已选活动举办时段重叠的项目时，保留原选择并说明冲突对象，让用户先取消其中一场再选择；不自动替用户取消活动。起止信息缺失或无法解析时标为“活动时间待确认”，不擅自判定为不冲突。

队列按报名开放时间排序，开放中的活动排在待开放项之前，已报名项保留在对应时间位置。下一场开放仍由完整活动集计算，不受搜索和筛选影响；它在队列中始终保留一条带“下一场”标记的记录。筛选不匹配时，这条记录仍置顶保留，而不是在页面其他位置复制一份摘要。无明确开放时间的活动归入“时间待公布”，不捏造时间轴位置。

用户确认同一开放时刻的计划活动要同时提交；不同时间的活动按各自开放时刻等待。执行中每场独立显示等待、提交、成功、失败或已取消状态；单场失败不隐藏其他场的结果。计划支持取消尚未开始的单场任务，也提供停止整个计划的入口。

当前 app.py 的 grab 接口每次只接收一个活动，且同一时间只允许一个子进程；grab.py 为单场活动等待开放并在开放后最多重试 120 秒。抓取数据中已有活动结束时间，但 docs/UI_SPEC.md 尚未把 act_end 列入活动字段，也未描述活动时段冲突规则。前端排队无法满足同刻并发，冲突判断也缺少正式数据契约。本方案因此要求先补齐活动起止时间与学校页面冲突规则，再增加后端计划协调器及多任务状态/事件契约，属于原 docs/UI_SPEC.md 所禁止的范围扩展；本次仅记录目标，不改后端源码。

## 视觉规范

### 色彩

| 用途 | 色值 | 说明 |
|---|---|---|
| 页面底色 | #F4F6F8 | 冷调纸白，作为队列的安静底面 |
| 内容面 | #FFFFFF | 活动记录和展开详情 |
| 主文字 | #172A3A | 深墨蓝，标题和活动信息 |
| 次级文字 | #566977 | 地点、辅助说明、次级状态 |
| 主操作 | #2456A6 | 清晰蓝，加入计划、启动计划等主要交互 |
| 开放时刻 | #E45B45 | 珊瑚朱红，时间轴焦点与下一场标记 |
| 成功 | #236B52 | 深青绿，登录有效、报名成功 |
| 忙碌 | #53677D | 蓝灰，登录或提交中 |
| 分隔线 | #D7E0E6 | 队列时间轴和记录边界 |

朱红只用于时间焦点与临近提醒，主操作使用清晰蓝，成功状态用青绿，避免整页被单一强调色吞没。浅色状态底上的文字使用深色，状态不能只靠颜色区分；成功、失败、忙碌同时配文字或图标。正文与底色按 WCAG AA 对比度目标检查。

### 字体与间距

字体回退顺序：Microsoft YaHei UI、Microsoft YaHei、PingFang SC、系统无衬线。标题 24px，区块标题 16px，活动名 14px，正文和控件 13–14px，辅助说明 12px；时间轴时刻使用 16px 等宽数字，倒计时使用 12–14px 等宽数字。正文不随视口宽度缩放。

以 8px 为基础间距单位；时间轴的刻度列固定宽度，普通队列行有稳定高度，计划选择有清晰复选状态。同刻活动共享时间轴刻度，底部计划条有稳定高度，不被队列滚动挤出窗口。按钮、筛选器和图标按钮尺寸固定。圆角不超过 6px，不用重阴影、装饰性渐变或无意义图表。

### 图标与动效

使用简明、易识别的线性图标辅助刷新、展开日志等操作；每个图标按钮均有可见提示文本或辅助技术可读名称。状态变化采用短促淡入或颜色切换，不使用循环装饰动画。遵循减少动态效果偏好。

## 组件和状态

| 组件 | 状态 | 展示与行为 |
|---|---|---|
| 登录状态 | 未登录、有效、临近过期、失效、进行中 | 显示对应状态和可理解的剩余时间；临近过期提醒但不遮挡主操作。进行中使用忙碌色。 |
| 时间队列 | 普通、悬停、计划中、未开放、开放中、已报名、时间待公布 | 按报名开放时间排序；相同开放时刻共享提交时间组。每项另显示活动举办起止时间。开放组不代表活动冲突；倒计时每秒变化不重排队列。 |
| 活动时段冲突 | 无冲突、冲突、时间待确认 | 对整个报名计划比较活动举办起止时段，不限于同一开放时间组。选择重叠活动时保留既有选择并说明冲突对象；用户先取消一场后才能加入另一场。缺少或无法解析起止时间时明确显示待确认，不标成无冲突。 |
| 活动筛选 | 搜索、状态、时间、排序 | 首次默认显示可报名活动；用户偏好保存后恢复。筛选不移除全局下一场计划项。 |
| 报名计划条 | 空、已选、准备启动、运行中、部分完成、完成 | 显示计划数量、同刻并发组数和不同开放时间组；当前已选活动存在举办时段冲突时显示冲突活动名并阻止启动，直至用户明确调整选择。支持启动、清空与停止整个计划。 |
| 计划任务 | 等待开放、提交中、成功、失败、已取消 | 每场状态独立展示；同刻组标明“同时提交”，不同时间分别等待。可取消尚未开始的单场任务。 |
| 操作结果 | 成功、失败、部分成功 | 逐场显示活动名、原因和下一步；单项失败不覆盖其他任务结果。不能只靠颜色传达。 |
| 日志 | 展开、折叠、空 | 默认呈现少量最新记录；展开读取完整记录。长内容换行或截断并允许查看，不挤占主操作。 |
| 空与异常 | 首次未登录、拉取失败、空列表、无筛选结果 | 每种状态分别给出原因和可执行的登录、刷新或清除筛选入口。 |

倒计时每秒只更新对应文本节点，不触发队列重排。多选计划中的活动按活动 id 去重。同一报名开放时刻的计划任务作为一个并发组同时启动；不同开放时间的任务由后端计划协调器按各自时间触发。举办时段冲突校验独立于开放时间分组，并在全计划范围执行。单项失败后继续显示其他任务状态，停止计划会停止尚未提交的任务，并说明已提交任务的当前状态。

## 关键文案

空活动列表：

    这里还没有活动
    点「刷新」拉一次；提示登录态失效就先点「登录」

报名成功：

    报名成功：<活动名>
    建议去活动页确认一眼

报名失败：

    没抢到：<原因>

原因保留学校页面返回的可理解信息；如登录态失效，提供“重新登录”；如网络失败，提供“检查网络后刷新”；如报名尚未开放，说明开放时间并保留必要的等待状态。避免连续重复“没抢到”前缀。

使用说明遵循三步：先登录、加入活动到计划、启动计划并保持在线。边界提醒：只给本人账号用，不要多开。计划摘要示例：“报名计划 3 场 · 18:47 同时提交 2 场 · 明天 09:00 等待 1 场”。

活动时段冲突：

    与「春季校园文化节志愿者招募」的活动时间重叠
    同一报名计划只能选择其中一场，请先取消一场再继续

开放批次提示：

    18:47 同时开放 3 场
    其中两场活动时间重叠，另一场时间不重叠，可与所选活动同时报名

## 无障碍与窗口适配

- 键盘可完成刷新、登录、筛选、选择活动和主要操作；焦点轮廓清晰且不被裁切。
- Enter 行为与当前焦点控件一致；F5 刷新活动列表，不意外触发报名。
- 登录、活动更新、操作结果通过状态语义播报；标签与输入控件关联。
- 状态文字与背景有足够对比；信息不只用颜色、位置或动画表达。
- 支持减少动态效果设置；界面不加载外部字体、脚本、图片或网络资源。
- 验证 WebView2 110+、980×700 最小窗口、1120×800 默认窗口，以及 100% 和 150% 缩放。

## 验收标准

- 首屏能辨认产品名、登录态、下一场开放活动、报名计划数量和启动计划操作。
- 多个不同时间的活动可以加入一个计划，并分别显示各自开放时间与等待状态。
- 同一开放时刻的多场活动在队列中形成提交时间组，并明确显示会同时提交；不把同刻开放直接视为活动冲突。
- 同一开放时刻下，举办时段重叠的两场不能同时加入计划并说明冲突对象；举办时段不重叠的活动仍可加入并同刻提交。
- 举办时段冲突检查覆盖整个计划，不因活动属于不同开放时间组而漏检；起止时间缺失时显示待确认。
- 主要工作区是按报名时间编排的连续队列；计划条固定在底部，页面不出现固定右侧操作栏。
- 活动筛选不改变全局下一场标记；筛选不匹配时该记录仍保留在队列内。
- 单场成功、失败、取消与计划整体停止分别有状态；部分失败不会丢失其他活动结果。
- 倒计时对应真实时间，不展示虚构进度；无可用时间时显示准确等待状态。
- 未登录、拉取失败、空列表、无筛选结果、成功和失败各有正确文案与下一步。
- 开放中、未开放、已报名三种活动状态可以快速区分；长名称和地点能完整阅读。
- 980×700 与 1120×800、100% 与 150% 下控件不重叠、无横向溢出，计划条和逐项状态易于找到。
- 通过键盘与可见焦点完成主要工作流；减少动态效果生效；页面无外部请求。
- 并发计划需由后端提供多任务协调、逐项状态事件、单项取消与整计划停止能力；活动时段校验需正式定义 act_start/act_end 的完整日期时间、缺失值与学校页面冲突边界；不以多个应用实例规避单任务限制。
- 视觉方向评审通过后，先更新 docs/UI_SPEC.md 和实施计划，明确开放时间分组、全计划活动时段冲突规则及 app.py、grab.py 的扩展范围，再实现和验证 UI 与后端。
