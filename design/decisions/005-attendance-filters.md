# 005 · 签到 / 签退三态筛选

- **状态**：implemented（规则 confirmed 2026-10-23）
- **日期**：2026-10-23 敲定（随活动打包信息扩展引入）

## 问题

活动有「要求签到 / 要求签退」两个要求字段，但学校接口对这两个字段的表述不稳定：
有的活动明确要求，有的明确不要求，有的接口根本没给。二值筛选会把「没给」误判成「无需」，
让以为不用签到的同学吃亏。

## 用户确认的规则

1. 字段是**三态** `true / false / null`：`null` 表示「接口还没说」，**不得降级为无需**。
2. 筛选语义：**全部**保留 `null`；**需要**只显示 `true`；**无需**只显示 `false`。
   `null` 在「需要 / 无需」两个筛选里都不可见，防止未知被误判。
3. 归一化只认明确别名；字段缺失、空值、未知字符串一律 `null`。
4. **筛选只影响时刻表可见行**：全局「下一场开放」、已选计划集合、冲突校验（含跨开放批次）、
   任务执行与结果全部基于全量数据计算，不得被筛选结果污染。
5. 筛选选择随偏好保存（`filter.checkin` / `filter.checkout`），下次打开恢复。

## 用户可见行为

- 筛选栏有「签到：全部 / 需要 / 无需」「签退：全部 / 需要 / 无需」。
- 字段未知时行内显示「签到待说明」「签退待说明」（两项都未知可合并为「签到/签退待说明」），有文字不只靠颜色。
- 勾了「需要」再开始计划，被筛掉的场次照样参与冲突校验与执行。

## 已知限制

- 「待说明」意味着学校字段还没确认；拿到新的真实别名样本时只扩 `CHECKIN_FLAG_NAMES` / `CHECKOUT_FLAG_NAMES`，不改三态语义。

## 2026-10-27 真实字段契约（confirmed）

真实详情接口 `GET /rjyHd/getInfo/{activity_id}` 已返回签到/签退契约：

| 字段 | 语义 | 真实样本 |
|---|---|---|
| `sfxyqd` | 是否需要签到（0/1） | 1 |
| `qdkssj` / `qdjssj` | 签到开始 / 结束 | 19:00 / 19:40 |
| `sfxyqt` | 是否需要签退（0/1） | 0 |
| `qtkssj` / `qtjssj` | 签退开始 / 结束 | 无 |

列表接口这三个字段全部为 `null`，因此「列表看不到」不等于「无需」。实现改为：
列表字段优先，详情在单次列表加载内按 `activity_id` 去重、并发上限 4 补充（每次刷新
是一个新的列表进程，进程内缓存只保证同一场不重复请求），单场失败只降级为
`attendance_state=pending`。文案从「待说明」细分为「签到信息同步中」（详情还没回来）、
「签到时间待确认」（详情已回来但没有数据）、「无需签到」（明确 0）。未知仍是未知，
不因为列表为 null 就画成无需。

## 变更方式
