# 004 · 多活动计划与举办时段冲突检查

- **状态**：implemented（规则 confirmed 2026-10-23，独立调度语义 2026-10-25 补齐）
- **日期**：2026-10-23 多活动计划敲定；2026-10-25 修正为「各场独立调度、互不阻塞」

## 问题

一次只抢一场不够：同学常常同时盯几场。但场次之间有两个正交维度——
**报名开放时刻**（决定什么时候提交）和**活动举办时段**（决定两场是不是撞车）——
早期「同一时间只跑一个任务」的设计把它们混在一起了。

## 用户确认的规则

1. **同一报名开放时刻**的多场活动：举办时段不重叠就可以**同时加入、并发提交**；
   重叠则提示冲突、只能选其中一场。
2. **不同开放时刻**的活动可以提前加入同一个计划，各自在自己的准备时刻启动：
   预报名在原定开放前约 100 秒，立即报名在计划启动后马上执行；**一场在重试中不得阻塞其他场次按各自时刻启动**。
3. 举办时段冲突按**半开区间 `[act_start, act_end)`** 比较：`a.start < b.end && b.start < a.end` 算重叠，起止相接不算；
   字段缺失、非法或结束不晚于开始的活动**不能进入可执行计划**。
4. 冲突检查覆盖**整个计划**，不因活动属于不同开放批次而跳过。
5. **单项失败隔离**：单项失败、已报名或取消只更新该任务，其他任务继续；每场保留自己的终态。
6. **停止**只取消尚未提交的任务，已提交场次保留真实结果；从确认停止到 worker 终止 ≤1 秒（进程树终止）；
   计划恰好发出一次 `plan_done`。**单场取消**随时可用（含等待中的场次）。

## 用户可见行为

- 多选活动后大屏给出计划摘要（几场预报名等开放、几场立即报名马上执行），逐场任务卡独立显示状态。
- 选重叠场次时提示「只能选其中一场」，已有选择保留，不自动替换。
- 停止走二次确认 → 「正在停止…」→ 各场落 canceled / 保留已提交结果；停后能一键把失败 / 取消场次重新选上。

## 已知限制

- 并发提交只发生在同一开放批次内；不同批次天然错开，不需要并发控制。
- 计划运行中不能再开始第二个计划（登录 / 单活动 / 计划共用一个「忙」判定）。

## 变更方式

调度语义改动集中在 `local/signup_plan.py`（`PlanCoordinator`、`_prepare_ts`），
必须带 fake clock 单测证明「不阻塞」语义；停止顺序改动需保住 `docs/UI_SPEC.md` §5.7.8 的 ≤1 秒验收条款。
